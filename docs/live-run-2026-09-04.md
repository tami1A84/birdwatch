# 実リレー --live 実走記録 (2026-09-04)

## 目的
`bin/nostrd --live` を実リレーに対して走らせ、gossip移植の中核(10002発見 →
evidence学習 → スコアリング → per-person割当 → REQ配信 → SQLite → unix socket)
が実データで機能することを検証する。

## 結論: 成功
- 90秒で **kind-1 を799件** 取得(3フォロー作者: 500 / 254 / 45件)
- ピッカーが実割り当てを形成:
  `nostr.mom(2) / relay.primal.net(2) / nos.lol(2) / nostr.land(1)`
  → **デフォルト3本(nos.lol, damus, nostr.band)の外の、フォロー相手の
  書き込み先リレーを自動発見・自動ダイヤル**(gossipのoutboxモデルの実証)
- 死んでいたリレー(nostr.wine)はハンドシェイクゲートで検出 → ペナルティボックス入り
- damusは一時的にハンドシェイク拒否(Cloudflare)→ ペナルティ → 後に自然復帰を確認
- unix socket 経由(TUIと同一経路)でライブタイムライン取得、アクション境界も確認

## 実走で発見・修正したバグ(計7件)
1. **`RelayPool` の本番transportが nil** — 「lazy: WsTransport」のコメントが嘘。
   `connect` 内で `@transport_class || Nostrd::WsTransport` に解決。
2. **orchestrator クロージャの初期化順依存** — `orchestrator = nil` 事前宣言 + `&.` 呼び。
3. **websocket-client-simple はコールバックを `instance_exec`** — gem側クライアントに
   再束縛されるため `@open_callbacks` 等のivarがnil。全状態をローカル変数に退避。
4. **死んだリレーがzombie接続になる** — `open` をハンドシェイク完了まで同期待ち
   (5sゲート)にし、失敗は raise → RescuePool が rescue → ペナルティボックス。
5. **`limit: 0` は strfry 系で「0件」** — kind-1配信REQから `limit` キーを削除。
   (10002発見REQの `limit: 1` だけが生きていた理由とも一致)
6. **Seeker が1リレーにしかSEEKしない** — `urls.first` は当たり外れで120sロスト。
   接続中全リレーへ fan-out(重複は `INSERT OR REPLACE` で吸収)。
7. **コールバック例外がEM/ダイヤルスレッドを殺す** — `on_event` / `on_disconnect`
   を `safe_call` で包む(ログ出力して継続)。

## 運用上の学び
- `pkill -f "bin/nostrd --live"` は起動コマンドを含む自分のシェルごと殺す
  (コマンドラインにパターン文字列が含まれるため)。**pidfile方式に統一**。
- EventMachine はプロセスで1つ。websocket-client-simple は接続ごとに reactor を
  起こすため、3本目で固着しうる → 現状は各リレーを独立スレッドでダイヤルし局所化。
  恒久対応は単一reactorのtransport v2。
- nos.lol は kind-1 の unlimit REQ で最大500件/REQを返す。

### 見つかったバグ(修正済み)
12. **`App#paint` が未定義** — `run` から呼ばれていたが実装が存在せず、
    初回描画で必ず NoMethodError になる(テストは headless のため未検出)。
    Renderer の差分再描画(`changed_rows`)を使って実装。ステータスバー
    (件数/選択/クエリ/キーマップ、色ペア)も追加。`:all` 時は clear 後に
    全行再描画する(当初 clear だけで描画漏れ)。
13. **`Curses.echo=` は存在しない** — echo 制御は `Curses.echo`(有効) /
    `Curses.noecho`(無効)というコマンド系メソッド。
14. **`Curses.getch` の二系統返値** — 印刷可能文字は String(マルチバイト
    UTF-8 対応)、制御文字は Integer。`when 32..126` だけだと文字が全部
    無視され、Enter(10)だけで空クエリ検索になっていた。String/Integer
    両系統に対応 → おまけで CJK 検索も通るようになった。
15. **Ruby 3.4 の PTY master が読み取り専用 IO で作られる** — カーネルの
    fd は O_RDWR だが Ruby のモードフラグが非書き込み。ハーネス側で
    `IO.new(fd, "r+b", autoclose: false)` で包んで解決(アプリ本体は無関係)。
    なお `pkill -f nostr-tui` は起動シェル自身にマッチする自己殺の再発あり
    (`[n]ostr-tui` トリックを使用)。

### アプリ本体への改良(検証ついで)
- getch に 250ms timeout → キー無しでもライブ新着が再描画される
- 矢印キー / PageUp / PageDown 対応(keypad 定数 → KEYMAP 変換)
- `/` を curses 内ラインエディタに(旧実装の `$stdin.gets` は raw モード下で壊れる)
- `y` yank を wl-copy 優先(omarchy は Wayland)、xclip フォールバック
- `n/r` は `Curses.close_screen` で端末を $EDITOR に明け渡し、`Renderer#reset`
  で全画面再描画

## EOSE後CLOSE + history設定化 (2026-09-04 22:51-23:05)

### 実装
- **SEEK系subをEOSE後にCLOSE** — `RelayPool` が `handle_frame` で `EOSE` を受けて、
  one-shot として記録した sub(seek/prof/self)を `transmit_close`。**リレー別に
  登録**(`@one_shot[url]`)するのが要点: fan-out は同一 sub_id を複数リレーに送るため、
  共有Setだと最初の1リレーで消えて残りが開きっぱなしになる。
  重複EOSEでも `on_eose` コールバックは発火し、CLOSEだけが抑制される。
  接続切断時にレジストリも破棄(再接続後の誤CLOSE防止)。stream系(subscribe_person)は継続配信なので閉じない
- **timeline履歴の設定化** — `Server#initialize(history: 100)` + `bin/nostrd --history N`。
  クライアントの `params.limit` 明示時はそちら優先。TUI は `subscribe_timeline` から
  硬codingした `limit:100` を削除(デーモン既定に任せる)
- ドキュメント: protocol.md(subのlimit省略時の挙動)、nostrd README(オプション一覧、
  「まだ無いもの」を現状に合わせ刷新 — RelayPool/NIP-49は実装済み)

## リレーに優しいREQ制御 (2026-09-05 01:05)

nos.lolから `notice: ERROR: too many concurrent REQs`。seek(kind 10002/0/3)を
**全接続リレーへ同時fan-out**し、person stream も上限なしで積んでいたのが原因。

### 修正
- **RelayPool に接続ごとの同時REQ上限(既定8)+ FIFOキュー**: 上限超過のREQは
  `queued` に入り、既存subのCLOSE(EOSE後のone-shot含む)で枠が空くとFIFOで開始。
  キュー中にキャンセルされたsubは送信されない。接続切断でキュー/スロットは廃棄
- **seek は1試行1リレー**: `seek_stale` / `seek_profiles` / `seek_own_contacts`
  は接続リレーをソートし、試行回数(バックオフ)でmod回転する1台だけに送る。
  見つからなければ次のバックオフ再試行が別のリレーに当たる。fan-out廃止
- `max_subs_per_conn` はテスト用に初期化引数化。REQ発行は全4種
  (person/inbox/10002/0/3 seek)が `queue_req` を通る

### 確認
- テスト: relay_pool +3(キャップ・キュー、EOSEで枠解放、キュー中キャンセル)、
  orchestrator +1(1リレー/試行の回転)。nostrd 合計 65/215 全green
- 実走: seek/prof/contacts が各1リレーのみに送出、NOTICE/"too many" 0件、
  投稿→ack→`sub:"live"` 自己エコー即時、スレッド5・ThreadError 0

## プロフィールがhexのまま問題 + ワンコマンド起動 (2026-09-05 01:23)

「フォローユーザーのユーザー名の多くがhexのまま」。kind 0 シークは回転していたが
**的中率と配信**に3重の問題があった。

### 原因(3件)
1. **シーク先が間違っている**: `seek_profiles` は接続リレー全てをアルファベット順に
   回転。しかし kind 0 は**その人の write リレー**にしか無いことが多く、正しいリレーに
   当たるまで 2分→4分→…→60分 のバックオフ再試行が必要。しかも全員 tries=0 なので
   最初のtickは**全フォロー分が同一リレー(urls[0])に集中**した
2. **空 kind 0 が鮮度を7日間汚染**: content が空/無効な kind 0(一部リレーが返す)でも
   profiles 行が作られ `fresh_profile?` が true に → **7日間再試行されずhexのまま固定**
3. **取得後もクライアントに届かない**: kind 0 が着地しても既存クライアントへの
   プッシュが無く(event随伴のprofilesフレームのみ)、TUIは再接続するまでhex表示

### 修正
- **シーク先の優先順**(Orchestrator#candidate_relays): `Store#person_relay_urls`
  (write宣言リレー → last_fetched の実績リレー順) ∩ 接続中を先に、残りを回転fallback
- **tickあたりのシーク予算**: `RELAY_SEEKS_PER_TICK=8` / `PROFILE_SEEKS_PER_TICK=6` —
  ログイン直後の最初のtickが1リレーへN連打しない(フォローリストをtickにまたいで歩く)
- **鮮度 = 使える項目を持っていること**: `fresh_profile?` は name/display_name/
  nip05/picture/about のいずれかがあること。空 kind 0 は取得済とみなさず回転の次の
  リレーへ。使える kind 0 の着地で `@prof_at` を7日間ゲート + 回転リセット
- **Server#broadcast_profile**: kind 0 着地のたび `sub:"live"` の profiles フレームを
  **単独プッシュ**(bin/nostrd の on_event で呼び出し)。TUIは既存の
  `apply_profiles` 経由で再ラベル(再接続不要)

### ワンコマンド起動: bin/nostr(リポジトリ直下)
- `nostr` 1発: ソケット死活を ping/pong 確認 → 無ければデーモンをバックグラウンド
  起動(nohup、ログは ~/.cache/nostrd/daemon.log)→ TUIをexec。TUI終了後もデーモンは

## 自己エコー死亡 + フォロー名の供給経路 + nostr:note: 残留 (2026-09-05 02:55)

実走(vault移行+再起動後)でユーザー報告: ①kind 1111返信の本文に

  post_comment 化で削除漏れ)。削除。
